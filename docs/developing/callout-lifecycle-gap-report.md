- **Bind and execute in Core.** The registry supports application-owned binding through `ChainBindingContext::bind_chain` (`crates/filter/src/binding.rs:413`). IRR builds nested step pipelines with the chain resolver (`crates/filter/src/builtins/http/traffic_management/iterative_request_router/mod.rs:333`). Existing tests cover named, inline, and missing chain references in a step (`crates/filter/src/builtins/http/traffic_management/iterative_request_router/tests.rs:5801`, :5840, :5872). Common instance-level ownership, capability validation, and the context-scoped client remain.
- **Chain-selected destinations.** The executor uses the upstream selected by a chain filter such as `load_balancer` for unstaged forwarding and fails at runtime if no upstream resolves (`crates/filter/src/filtered_subrequest/mod.rs:1133`). A local rejection or response bypasses peer lookup and is converted into a response (:1032, :1644). Staging both destination types is rejected. Staging a cluster pins the endpoint Core selects for the attempt, with retry reselection under cluster policy. The staging API does not take a caller-selected endpoint (`crates/filter/src/filtered_subrequest/staged_cluster.rs:32`, `crates/filter/src/filtered_subrequest/attempt.rs:319`). Load-time detection for provably destinationless forwarding remains.
- **Responses MCP migration.** The executor already pins prepared URL targets and exposes streaming responses (`crates/filter/src/filtered_subrequest/mod.rs:771`, :864). Core still needs common binding and the scoped client with load-time streaming compatibility validation.
- **Broker in an outbound chain.** Core still needs completion for the child pipeline (`crates/filter/src/filtered_subrequest/mod.rs:815`) and common binding and client ownership (`crates/filter/src/binding.rs:413`). Chain-selected upstreams and local responses already use the executor paths above.
- **Second caller.** Buffered and classified response APIs already exist (`crates/filter/src/filtered_subrequest/mod.rs:627`, :734). The common client still needs to preserve direct behavior and typed outcomes for callers that use these APIs.

### Completion status decision

Current executor calls can return a synthetic HTTP response on failure before upstream headers. A transport failure is classified into a status and returned as a response (`crates/filter/src/filtered_subrequest/mod.rs:1439`). An in-flight deadline can return HTTP 504 (:1547). The requirements specify both the caller-visible status and zero for pre-header failures. Confirm whether completion should report the synthetic status that the caller actually receives, or use zero for all pre-upstream-header failures even when the caller receives a synthetic HTTP response. The first interpretation uses zero only when the executor hands the caller no HTTP response and preserves both the existing API behavior and the hook's “no status written” meaning.
